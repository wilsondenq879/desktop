# 先說明、後繪圖與生成速度

## 架構圖

架構圖回答先給 2–3 句簡短繁體中文設計說明，再呼叫原生繪圖工具。
伺服器以句子邊界放行正常文字，不再把所有內容暫存到圖片完成。
遇到分段的程式碼圍欄、JSON、SVG 或繪圖程式碼便停止文字預覽；原始資料保留供安全的 JSON 復原，絕不執行模型程式碼。

架構圖先用相同模型進行一次小上下文、無工具的短答（最多 320 token、8 秒逾時），
再進入完整工具繪圖。短答在主串流第一個事件就顯示，不需要等工具參數全數生成。
短答失敗／逾時仍繼續主流程；模型若省略前言，完成的節點／連線資料也可提供確實對應該圖的說明。
最終內容保留已顯示的說明及圖片；小上下文短答的可用解碼統計也納入速度平均。
這改善顯示等待感，不會消除模型本身的排隊、載入或思考時間。

### 不支援原生工具呼叫的模型

已觀察到 `gemma4:26b-mlx` 有時只產生描述或 SVG 字串，沒有執行 renderer。
此模型的明確架構圖請求改為 JSON-schema 約束的資料規劃，伺服器呼叫真正 renderer。
一般聊天不變；其他模型仍用原生工具，未提交成品時再做一次限時資料化備援。

Open WebUI 0.12.3 在 `inlet` 後還會注入內建工具與完整 skills 目錄，因此僅在 inlet
清除工具不足。資料模式也必須在最後的 `request` hook 固定規劃資料格式，移除後加的
工具／shell 指令。此模式限已觀察到不相容的模型、明確架構圖問題，不全域停用 tools。
繪圖 JSON 永不顯示為回答；驗證需確認實際圖片存在，而不是模型說已完成。

### 跨層路由修正

WebUI renderer 的節點、連線端點與走線間距使用一致的 36px 網格；端點間距設定
只套用於 WebUI 產生的圖，不更改一般上游範例的 18px 預設。候選走線先排除過短
線段及過多轉折，不再先選到 3–9px 的短折線，最後才把整張圖拒絕。
合法跨層繞行允許最多 4 次轉折與 1.8 倍繞行，仍維持零交叉、至少 16px 線段。
同層雙向連線分別走上、下方，避免互相交叉。

實際 Gemma 原題已確認先行文字、PNG 200、全部設備連通、GX10 與工作站分開及
content/output 重開一致。新增單元測試及三種實際路由成品測試通過。
上游完整套件目前跑 141 項，5 項略過，14 個快照檢查未通過；未更新快照來掩蓋差異，
不可將上述 WebUI 驗證描述為上游全套測試通過。

## 每則完成回答的 tokens/s

全域 Filter `openwebui_response_speed` 排在繪圖與術語校正之後，程式計算而非提示模型自行填數字。

1. Ollama：`eval_count / (eval_duration / 1e9)`，duration 單位為 ns。
2. llama.cpp：`predicted_n / (predicted_ms / 1000)`，duration 單位為 ms。
3. 多次模型生成：依完成 ID 去重，以總 token／總解碼時間計算加權平均，不含繪圖／工具等待。
4. 只有供應端每秒速度：使用供應端回報的最後一輪。
5. 只有實際 output token 數：除以請求開始至結束時間，包含等待與工具，以 `≈` 區別此端到端估計，不能當純解碼速度。
6. 統計不完整：N/A，不用字數假冒 token 數。

解碼 token 可能包含模型思考及工具參數，不等於使用者看到的中文字數。
完成回答只顯示 `55.0 tokens/s`；不輸出 HTML 註解標記、標題或長說明。無統計時顯示 `N/A tokens/s`。
只修改當次回答，保留工具歷史與舊訊息；content 與 structured output 同步存檔。

部署：runtime venv 執行 `scripts/deploy-response-feedback.py <runtime>`，先備份資料庫再透過版本化 API 更新。
測試：runtime venv 執行 `scripts/test-response-feedback.py`，再執行原本圖表回歸測試。
`scripts/verify-diagram-live.py --expect-intro --expect-speed ...` 透過真正 Socket.IO 串流驗證文字先於繪圖狀態，並檢查速度與重開對話。
